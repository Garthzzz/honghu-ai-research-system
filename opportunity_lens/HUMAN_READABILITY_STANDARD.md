# Opportunity Lens 人类可读性契约 V2

本文件把工作流精简前已经成立的 C 轨页面职责和 agent 工作模式，与现行 V2 数据/发布门禁及用户最新写作要求合并为一份活动合同。共同研究写作规则见 `templates/数据呈现与重写标准.md`；精简前原件只用于核对规则来源，不再作为动态事实源。

## 1. 总体原则

- 本合同规范公开研究内容的组织、措辞和数据呈现，不授权修改 Viewer 信息架构。同一产品不同 run 默认复用 `MODULE_CONTEXT.md` 声明的稳定产品合同、页面骨架、导航、路由、页面分工和交互；内容可在既有区域内自适应。结构变更必须由用户明确提出，并单独完成全部稳定路由的兼容审查。
- Run 入口和页头使用简短、准确的 `display_title`；完整 `research_question` 保留在研究包和入口合同中，正文必须覆盖其全部 requirement matrix。页头可用一句自然中文 `problem_statement` 补充语境；不得把完整长请求直接当页头标题，也不得用机械截断造成主体或研究对象缺失。
- 页面首先回答研究问题，再展示审计细节。
- 人类阅读顺序固定为“结论或状态 → 这个模块回答的业务问题和必要解释 → 公式/计算口径（如有）→ 可点击证据与来源”。生产字段和审计载荷不得抢在研究判断之前。
- 原始 JSON、URI、`source_id:` 字段和机器枚举不得出现在用户页面，即使是折叠层；原始结构留在只读 API、内部 manifest 和数据库审计接口。短 `^src` / `^evidence` 按钮可以使用紧凑索引，但必须有可读标题提示并能打开完整证据抽屉。
- 所有机器枚举有中文显示；ticker 同时显示主体名称。
- run 总览只放最重要的判断、少数表格和图；全量数据留在实体、证据库和 API。主报告不得完整复制实体页、标的页或证据页正文，应概括跨主体结论并链接到只出现一次的详细分析。
- 合成 fixture 明确标注为示例，不能与正式研究混淆。

## 2. 正文章节合同

每个面向用户的章节和实体专题都要显式使用四个可见小标题，不能只在内部写作顺序上暗含这条链：

1. **问题**：本节具体回答什么，不粘贴整段用户请求；
2. **研究方法与数据**：哪些证据、数据、比较或计算真正约束问题；没有复杂计算就不硬加公式；
3. **研究与分析**：事实如何传导到判断，反方证据和数据缺口怎样改变结论；
4. **总结**：用直接、可独立阅读的中文写清主体、时间、事件和影响，可用加粗突出核心判断。

四个部分必须各自成段；“研究与分析”较长时继续按论点拆段，禁止把整章压成一个视觉上连续的大段落。充分检索后仍有关键数据客观不可得时，在“研究与分析”中说明已查范围、采用的近似、结论影响和置信度。正文不让读者从状态表、字段矩阵或来源堆叠中自行拼答案。研究生产和审计所需的字段完成度、覆盖卡、参数名称、参数 owner、内部情景代码、任务状态、证据 URI、canonical/intake 名称只留在 manifest、底稿或内部 API，不进入公开正文。

公开语言必须有明确主体、时间和事件。禁用“本节结论状态与专属边界”“决策含义”“下一次更新”“最低可证含义”“不可推出”“破坏程度”等模板标签；“一页执行摘要：概率、破坏度与投资含义”“联合情景树、概率更新与破坏程度”“决策验证债”“七字段事件监控 dashboard”等旧标题也不得换个位置继续复用。取消“如果想进一步研究，需要补充的信息”标准栏目，它不能成为延后本轮搜索和回答的出口。改写为自然句，例如“根据现有证据，可以认为……”“目前还没有直接证据证明……；这使该结论只能保持中等置信度”。不得用 `[未知]` 表示证据缺口：分别写明没有直接证据、公开资料不足，或无法根据现有资料推断，并解释对结论的影响。

## 3. Run 页

- Run 页必须复用 `MODULE_CONTEXT.md` 定义的稳定页面族和导航，不因 pack/schema 版本另起公开信息架构。schema 专用模板只可承担数据适配，不能改变用户看到的页面职责和阅读顺序。
- 身份、状态和紧凑 KPI 之后，公开阅读顺序为“研究报告（全宽）→研究对象→因子热力图与结构化总览→长期序列可视化总览（仅适用时）”。一屏研究概览可以放在报告之前，但不得成为营销式 hero，也不得把报告、对象和追踪页面挤掉。
- “研究报告”必须独立回答完整问题；“研究对象”只提供摘要与入口，详细实体分析只出现一次。不得把实体全文再次粘贴进主报告，也不得因为避免重复而删去实体页、因子页、指标槽页、审计页、补充研究页或导出页。
- 高分机会矩阵默认只显示编号；名称只在 hover/focus 的上层浮层出现。
- `theory_research` 不进入机会矩阵，不显示 0 分占位。
- 核心排序表的判断、证实条件、证伪条件和动作必须逐实体差异化。
- 长期序列独立成板块，桌面最多两列；只有真正长周期且趋势有解释价值的因子做图。
- 热力图必须有可区分色阶、图例、中文因子名和数值；证据稀疏时可以用表替代不适合的图，不能退化为同色进度条或为了凑图制造视觉模块。
- 宽表提供顶部同步横向滚动条。

## 4. 实体页

市场型实体依次回答：研究对象、证据链与数据基础、分析、总结、相关标的与投资研究建议。

理论型实体依次回答：研究问题、范围、方法、文献综述、数据收集、研究指标与计算底稿、分析、回答、总结、限制。

证据链必须用连贯分析写清：

1. 证据事实；
2. 证据之间的支持、约束或冲突；
3. 现有证据能把结论支持到什么程度，以及缺少的信息会怎样改变判断；
4. 对评分、标的、证伪或补证路径的影响。

不得退化为 source bullet、字段完成表、摘录堆叠、URI 列表或“请阅读全文”。招聘、专利、客户验证和产能信息应先归纳进展及相互印证关系，再用少量必要表格保留关键时间点；“某字段为空所以不能推出某结论”属于内部审计语言，公开正文应直接说明现有证据能支持到哪一步。

## 5. 概率、模型和公式

- 先用一句话定义事件和期限，再说输入数据、方法、结果与局限。
- 先验、众数、分位数、Monte Carlo、Wilson 区间、相关结构等术语只有在改变判断或允许复算时才进入正文；首次出现必须用普通中文解释，不能要求读者理解 `low/mode/high`、P10/P90、Fréchet 或内部变量名。
- 概率表优先只保留“主体/事件、3 年判断、5 年判断、主要依据、什么证据会改变判断”。如果分位数不能改变决策，就不展示。
- 公式使用正常数学排版或可读算式，并紧邻解释每个变量、样本、运算和输出；禁止把 `$center=(...)$` 一类源码直接交给用户。
- 展示单位发生变化时必须同时做数值换算，不能只重命名单位标签。例如 `USD bn` 转成“亿美元”时数值乘以 10，`million units` 转成“万个/亿个”时按量纲换算。公开表发布前至少执行字段单位、显示单位、代表值反算和数量级常识四项检查；关键换算必须有自动化回归测试。
- 共同起点或相同参数必须解释为什么相同；没有可辩护理由就应使用主体差异化输入。模拟精度不得掩盖认识不确定性。
- 情景和架构必须使用完整中文名称。内部 A—F、P/H/C、D0/D1/D2 等代码只能留在底稿，公开正文不得要求读者对照记忆。
- 同一报告出现名称相近但计算合同不同的概率或损失分类时，必须分别说明输入、条件分母、计算方法和用途，并直接告诉读者两者不是同一套结果。结构化专家权重必须标明不是外部事实，说明残差档位如何得到、是否经过历史或财务数据校准；不得把专家权重写成财务阈值反算结果。
- 正文引用本地模型输入或输出底稿时，run pack 的对应 source 必须保存文件内容 SHA256。只有路径而没有内容哈希，不能证明 reviewer 审核的是发布时使用的假设。
- 对多层乘积、加权汇总、跨期递推、概率传播或其他难以用短句准确描述的核心模型，在“建模方法”“计算方法”或自然等价栏目中集中写出一至三个最关键的可读公式，再解释变量、输入、输出、量纲和局限。简单四则运算、已经能用一句话说清的关系及不改变读者理解的中间步骤不单独制成公式；禁止把底稿公式清单整体搬进公开正文。
- 当同一问题包含时序数据、公司历史与预测财务、多个业务分部或多个情景，并同时比较两个以上指标时，若连续文字会迫使读者来回对应，应优先合并成一张高信息表，再在“研究与分析”中解释趋势、差异和原因。相关数据能放进一张表时不得拆成多个小表；短序列、单指标或正文更清楚时不制表，也不能因为有一组数字就机械增加表格。
- 每个 topic 的图表数量由问题和信息增量决定，不设机械的一图上限，通常不超过三张。财务时序、业务分部、情景和估值结果若可在同一图或同一高信息表中清楚比较，应先整合；只有量纲、问题或视觉负担明显不同才拆开。

## 6. 财务、估值和情景

- 公司结构化历史财务、市场估值、一致预期、公司指引、内部预测和市场隐含结果来自独立 `financial.db`，不同 fact type 不得混成一个数值；研报或旧普通数据点只能作为有明确来源层级的兼容证据。
- FY1—FY3 内部财务预测必须先冻结输入、公式、代入、输出和 SHA256，再展示 Wind/Tushare 一致预期或研报差异。正式估值必须说明适用性门禁、估值日和预测年份、每个输入的来源/时间、软调整桥、结果区间、敏感性和外部对账；没有计算过程不能称为正式模型。
- 公司财务建模的卖方预测对账只使用研究截止日前最近两个季度发布的同一公司报告。公开比较必须写出机构和发布日期；更早报告不进入当前中位数。停止覆盖报告只保留其截至当日的最终模型并标明状态，数据商一致预期单列，避免与可能重复收录的卖方报告双重计权。
- 已解析 `company_id` 的上市公司，在每个独立正文段落第一次出现时链接到 `/company/<company_id>`。母子公司、A/H/ADR或经营承载主体不同，必须先解释财务归属再链接。Wind/Tushare/yfinance请求、代理错误、重试和逐字段补缺只留在审计层；公开正文不写生产过程，只写最终口径、客观缺口和结论影响。
- 多家公司若基数、现金转换或风险传导不同，历史财务、未来情景和投资判断分别呈现；不能为了少一张表牺牲主体可读性。复杂公式必须同时给出真正代入模型的关键数值、来源或判断依据和结果；本地材料缺少未来利润、市值、PE/PB、ROE/ROA等重要对账时，继续搜索可核验的最新资料，仍不可得再说明边界。
- 实体页必须分析事件对该主体自身的短期与长期收入、利润、现金流、资本开支、上下游和估值影响；多个受影响公司分别形成专题、情景结果和条件化投资结论。PB—ROE/PB—ROA只在适用时解释资产回报、杠杆和PB，不得作为无分析的装饰组件。
- 公司筛选与组合类研究按读者的投资决策顺序组织：先研究细分行业、产品、客户、合同/订单/部署和商业化，再验证逐公司的收入、利润、现金流、资本效率与市场定价，最后才做公司排序、权重和对冲。进入候选排名的公司不能只列名字。销售AI产品的公司逐家回答付款人、购买内容、签约/启动/上线/验收/收入/回款阶段、续费原因和可复制客户池，并把合同经收入确认、增量毛利、交付/推理成本、营运资金和资本开支传到自由现金流；使用AI赋能经营的公司逐家核验实际采购或部署成本、效率/产能/服务变化、用工变化、回收期及其短期和长期财务传导。公司案例效率不是独立审计结果；价格不可得时做客户侧盈亏平衡敏感性，不把案例数外推成公司收入。证据不足者可以标为经营对照，但不得获得精确权重；通用公司简介和“继续观察”不能代替研究结论。
- 组合方法必须公开逐公司的经营与估值评分、基础锚、主动调整、约束和最终权重之间的桥接；相关性、波动和再平衡细节只保留会改变决策的部分。最关键的复杂公式必须单独使用 `$$ ... $$` 展示并解释变量，不得与长段文字挤在同一行。
- 上市公司研究若已形成可复算的独立预测和估值结果，研究交付还要尽量把 FY1—FY3 预测、适用估值方法和反向市场预期同步到公司详情页；同步使用 `company_financial_profile_export.v1`，不能从正文表格二次手抄。若现金流桥、净资产桥或目标倍数依据不足，只展示诊断/参考结果并清楚写明限制，不把它包装成正式目标价。
- 事件概率与条件财务冲击分开：事件概率说明情景成为现实的可能性，收入/利润表展示“在该情景已经发生的条件下”如何由业务暴露、份额、价格、成本和费用传导。除非明确做期望值且解释用途，不得直接用主观概率乘收入或利润。
- 多模型先按共同经营假设归为利润倍数、企业价值、资产回报和诊断模型簇，解释集中和冲突，不机械平均。DCF 缺未来 CAPEX、折旧、营运资本、税率和三表闭环时必须关闭或降级为敏感性/反向 DCF。
- 历史财务优先合并为一张核心对比表；清楚标明主体、期间、单位、实际值/预测值和来源。
- 未来分析必须把估计方法、关键假设、结果、差异原因和对估值的影响写足，不能让完成度矩阵或参数表占据主要篇幅。当章节回答某一事件对竞争格局和长期盈利的量化影响，且模型已经形成跨主体、跨情景或跨期限结果时，应优先用一张高信息比较表展示比较对象、期限、基准值、变化值或变化幅度，以及与问题直接相关的收入、毛利率、净利润、自由现金流或估值影响；表后再用正文解释原因和结论。
- 减少低信息表格不等于禁表。默认优先合并为一张核心历史表和一张未来情景结果表；能显著提高比较效率或允许复算的结果表必须保留。敏感性只有在确实改变结论或决策时才展示，可以用至多一张表，也可以用更清楚的量化正文；没有额外信息增量时不得为了凑表制表。超过三张时，每张表都必须说明不可由其他表替代的信息增量。
- 同一行或多列数值大面积相同必须独立复算并解释是共同输入、四舍五入还是错误；没有解释不得通过 calculation/financial/final review。
- “基线路径”“本轮代理”“受影响参数”“参数 owner”等内部字段不得公开。敏感性列名直接写对收入、利润、自由现金流或估值的影响。

## 7. 因子页、指标槽页和底稿

- 因子页必须独立完成四项任务：先说明该因子回答什么问题和当前分数意味着什么；再解释公式、输入、覆盖度与置信度；随后展示具体原文、来源、日期及上下文解读；最后列出指标槽及可点击追踪入口。公开页不展示原始 trace JSON。
- `factor_value_summary` 回答当前分数意味着什么。
- `information_points[].interpretation` 回答该条原文的背景、对本因子的贡献、与相邻因子的关系以及对具体标的或研究边界的影响；“请结合全文阅读”不算解读。
- 指标槽页必须说明预期指标/单位/期间、选中了什么证据、排除了什么证据及原因、为什么缺失或不适用、标准化和计算过程，并能回到因子页和证据抽屉；不得只是跳回 run 页。
- 同一底层来源以 URL、`opp://` 或 A/B 引用多种形式出现时，在 resolver 边界归一，不得在信息卡重复计数或重复展示。
- `opportunity_research_data_point.interpretation` 与 `research_use` 不得相同，也不得整列重复。
- 底稿存在不能替代正文解释指标设计、公式、输入、权重和结果含义。

## 8. 标的页

- 每个标的有独立页面和 API，展示主体/ticker、标的介绍、与研究实体及主问题的关系、暴露逻辑、深度研究、入库数据点、财务/市场状态、同实体比较、主要风险和条件化建议。
- 投资观点、风险、证实动作、证伪动作、相对偏好和研究动作不得全表同文或只替换公司名。
- 标的数据来自公司篮子而非标的自身时，明确标注“同实体公司篮子对照，不代表该标的自身财务”。
- 金额统一亿元人民币（约 xx.xx 亿美元），倍数/比例保留两位小数。

## 9. 审计、补充研究和导出页

- 审计页负责质量门禁、问题、严重度、受影响对象、处理状态和可追溯复核；公开研究正文只保留会改变结论的风险，不把字段完成度或内部状态矩阵搬进正文。
- 补充研究页仅承载独立发起的补证任务和用户追加资料，不是主报告的标准末尾栏目，也不能代替本轮 requirement 回答；页面内容说明缺什么、为什么影响结论、优先查什么、用什么公开来源验证，不得用 `下一次更新`、参数名或任务 owner 代替人类可读问题。
- 导出页负责当前 artifact、manifest、版本和导出任务状态。没有真实 PDF renderer 时必须明确说明，不能把 HTML 或 export job 表述成已生成 PDF。
- 三类页面必须是独立 GET 页面，不能用重定向回 run 总览冒充实现；普通 smoke 不触发写入、刷新或导出。

## 10. 来源和引用

- 事实句尾使用短 `^src` / `^evidence` 按钮，点击打开证据抽屉。
- 证据抽屉按固定的人类顺序显示：证据对象类型；指标/期间/数值/单位（如有）；来源标题、发布方、日期和级别；本轮使用的原文与中文译意；原始链接按钮；必要的字段/口径说明。原始 JSON 和机器 URI 不在公开抽屉展示。
- 文末来源索引使用可读标题、发布方、日期和可点击引用；内部 source id、记录号、表名或其他机器定位字段不得作为单独信息列公开。
- 英文来源的中文标题与译意必须由研究生产阶段显式写入，不得把“未命中人工译句，请自行阅读”类占位说明当作翻译通过验收。
- 正文不暴露裸 URL、磁盘路径、`opp://source/`、`source_ref:`、`原文地址：` 或原始 JSON。
- `$1 trillion`、`$20bn`、P/E、P/B 和百分号按普通文本显示，不触发 KaTeX 或逐字符断行。
- 非权威新闻、公众号、论坛、社媒、招聘和展会材料可以作为搜索线索，但公开正文引用它们时必须说明是线索而非确认；优先引用其所指向的原始专利、公告、产品文件、客户/供应商或官方展会资料。多篇同源转载不能写成“多方证实”。
- 对多方反复提及但尚未得到强证据闭环的重要主张，正文可以保留一段简短分析：明确“市场上存在这一说法”，写出最早可见出处、支持与冲突、已经核验的范围、目前为什么不能确认，以及若属实会怎样改变结论。不得把这类线索写进已确认事实表，也不得用它直接驱动概率或财务结果。

## 11. 表格信息价值与浏览器验收

- 每张表必须对应一个已写明的问题。删除某列后若不影响事实理解、计算复核或决策，该列必须删除；两张表回答同一问题时必须合并。公开页不得展示输出覆盖卡、字段完成矩阵、参数归属表或纯审计 dashboard。
- 表格最后一列不能承担整段结论；复杂判断写在表后正文，表内只保留能横向比较的短句。
- 观测、分数、状态、排名、优先级紧凑；来源、原文、计算、判断和动作获得主要宽度。
- 所有长表在局部 `opp-wide-scroll` 中，顶部 mirror 与正文 `scrollLeft` 实际同步。
- Playwright 至少检查 run、理论实体、市场实体和含英文金额/ETF 的证据页，覆盖桌面和移动。
- 浏览器审计必须枚举每一张公开表，在桌面和移动端分别截图或读取几何边界；滚动到最左和最右两端，确认最右列表头与单元格完整可见、无重叠、无裁切。仅检查 `scrollWidth > clientWidth` 或路由 200 不算通过。
- 浏览器审计必须形成结构化产物，记录脚本版本、当前研究包哈希、Viewer 代码与资源组合哈希、全部路由、桌面/移动 viewport、逐路由表格数、逐表左右端点与最右列几何、整页溢出、键盘可达性，以及每张表滚到最右端后的局部截图与哈希。每个路由的全部唯一证据引用必须用 Enter/Space 实际打开，记录证据 API 状态、抽屉可见性、横向溢出、可读标题、禁用机器词检查和代表性抽屉截图哈希；来源级别、日期和时效提醒必须翻译成人话。缺少任一必需字段或与当前产物哈希不一致时，browser review 不得为 GREEN。
- 表格列宽必须服从语义：主体名称优先保持一行，长结果列可按实际内容缩窄或局部滚动。图表按“主体＋指标＋报告期＋口径”去重经济观测，兼容层重复记录不能形成重叠标签；browser review 在双视口检查标签几何和实际截图。
- DOM 断言：可见正文无机器 URI/原始 JSON/内部情景代码/审计字段；公式没有源码泄露；底稿解读与用途不相同；无整页横向溢出。
- 卡片、热力图和矩阵中的因子名称必须在卡片本身完整可见。名称应获得独立行或足够宽度，不能被分数/状态徽标挤压，也不能依赖 `title`、hover 或详情页补全。双视口审计需要检查每个标签的 `scrollWidth/clientWidth`、`scrollHeight/clientHeight`、可用宽度及其与徽标的几何重叠。
- `<details>` 内完整性检查使用 `text_content()` 或先展开，不能用不可见元素的 `inner_text()` 判空。

## 12. Agent 任务与审查合同

所有 C 轨 producer、定向修复 agent、writing/browser/final reviewer 的任务上下文必须包含本文件、`MODULE_CONTEXT.md` 和与 artifact 对应的顶层 C 轨基础协议。不得把某个旧 run 的产物结构当作 agent 指令来源。

涉及新近、争议或证据稀疏问题时，producer 必须获得额外检索资源，并执行“宽搜索、严验证”：允许从弱源发现线索，逐条追溯原始来源，核对主体/产品/时间/数量，从客户、供应商、专利、招聘、设备、政府、展会等不同链路寻找独立侧证，同时搜索否认和替代解释。任务结果必须区分原始证据、独立侧证、同源转载和重要未验证线索。已有研报和用户 seed 不能降低这一要求。

evidence reviewer 必须检查搜索是否因已有研报过早停止、关键市场说法是否追到最早出处、所谓多源是否共享底层来源、未验证重要线索是否被错误删除或升级；writing/final reviewer 必须确认公开说明既不把线索写成事实，也没有隐去会显著改变判断的争议信号。

生产和审查是闭环：来源/数据 producer 后接 evidence reviewer；模型、评分、概率、公式和财务 producer 后接 calculation/science/financial reviewer；公开正文 producer 后接 writing reviewer，并在 writing stage 内执行 citation verification；Viewer producer 后接 browser reviewer；全部定向问题闭环后只做一次综合 final review。Nature/严谨性视角检查来源独立、方法复现、反方和边界；基金经理视角检查研究是否改变风险收益判断、标的优先级和证实/证伪动作。任何一项失败都打回对应 producer，不通过前端隐藏、删字段或改样式绕过。

writing reviewer 既查语法，也查读者是否能直接理解问题、证据、计算和结论；browser reviewer 必须做全部稳定路由、双视口、逐表最右列和逐证据抽屉审计；final reviewer 必须删除低信息表格和机器字段，而不是只确认字段齐全。evidence、science、calculation、financial、writing 和 final 的输入哈希必须绑定当前研究包；browser 的输入哈希必须同时绑定当前研究包与 Viewer 代码/模板/CSS/JS。产物或页面资源发生变化后，旧 reviewer 记录立即失效，不得继续用于发布。

审查发现系统性问题时优先修复协议、字典、read model、构建器、模板、CSS/JS 和测试的根因，不能只改一个页面上的句子。每轮交付前再次自问：问题是否被完整回答、关键反方和数据边界是否遗漏、计算能否复算、页面是否仍承担原有产品职责。
